# Rust conventions

DirkEngine follows the shared engineering standard,
[sourceorigin-standard](https://crates.io/crates/sourceorigin-standard), also
used by piqueld and sourceorigin. `just standard` checks its rules, and
`standard.toml` lists where DirkEngine departs from one, with its reason. This
page holds what DirkEngine adds that no rule checks.
Keep implementations simple, follow neighbouring modules, and share repeated
logic instead of copying it.

## Crates and boundaries

Libraries live in `crates/` and binaries in `apps/`; the root `Cargo.toml` is
a virtual workspace. Each crate owns one part of the engine (see `AGENTS.md`
for the map), and dependencies point down: `dirk_utils`, `dirk_threads`,
`dirk_proc` and `dirk_build` at the bottom, then `dirk_events` and
`dirk_universe`, `dirk_engine`, the feature crates (`dirk_assets`,
`dirk_platform`, `dirk_input`, `dirk_world`, `dirk_player`), and
`dirk_renderer` and `dirk_editor` on top, and the `dirkengine` binary in
`apps/` above them all. `dirk_rhi`, the render hardware interface, depends on
no engine crate but `dirk_shaders` and the bottom ones. Never add a dependency
that points up.

Platform and graphics libraries stay behind the crate that wraps them, and
`deny.toml` bans them elsewhere: `ash` and `gpu-allocator` in `dirk_renderer`
and `dirk_rhi`, `winit` in `dirk_platform`, and `egui` in the editor and the
crates that feed it. Add a new library of that kind to its ban list.

A feature enters the engine as an `EnginePlugin`, which configures the
`EngineBuilder`: it registers subsystems, ECS systems, events and editor
panels, and requests the plugins it depends on with `with_plugin`. State the
engine loop drives lives in a subsystem; `crates/dirk_engine/src/subsystem.rs`
describes the lifecycle.

## Features and platforms

The `editor` feature adds the editor to the engine, the renderer and the
player, and `cli` the binary's command line; both are on by default. Code
behind a feature must build, lint and pass its tests both with every feature
and with none (`just lint`, `just test`, `just test-minimal`).

Platform-specific code uses the compiler's built-in `target_os` cfg, such as
`#[cfg(target_os = "macos")]`.

## Errors

Each crate with fallible operations has an `errors.rs` with one `thiserror`
`Error` enum and a `Result<T>` alias. Variants keep their source with
`#[source]` or `#[from]`, and wrap the errors of the crates below them, as the
renderer's `Error::Platform` and `Error::AssetError` do. `anyhow` is for the
places where errors from many crates meet: plugin and subsystem callbacks, the
binary and its CLI, and the editor. Add `.context` to each step there.

Production code never panics: no `unwrap`, `expect`, `panic!`, `todo!` or
`unimplemented!`. Return an error when the input can be wrong, such as an
unsupported glTF image format. An invariant the types can't express takes an
`#[expect(clippy::expect_used, reason = "...")]` on the smallest item around
it, saying what guarantees it, such as `"Only Drop takes the allocator."`.
Tests may panic, through an `expect` that says what should have held; `unwrap`
is never allowed (`clippy.toml`).

## Lint exceptions

Never `#[allow]`. An exception is `#[expect(lint, reason = "...")]` on the
smallest item, and the reason says why the lint is wrong there, such as
`"Window extents fit exactly in an f32."`. Code that is only dead in some
builds says which: `#[cfg_attr(not(feature = "editor"), expect(dead_code,
reason = "..."))]`. Code generated by `dirk_proc` is the one exception: it
emits `#[allow]`, since an `#[expect]` would warn in every expansion that
doesn't trigger the lint.

## Unsafe code

Only `dirk_renderer` and `dirk_rhi` may use `unsafe`, to call the native
graphics API (Vulkan through ash), and `dirk_rhi`'s native tests, for its
unsafe host access to buffers. It stays in the modules `standard.toml` lists
in `unsafe-modules`, each of which expects `unsafe_code` with a reason;
`just lint` denies it everywhere else. Keep it in the modules that wrap a
native object, and give every `unsafe` block a `// SAFETY:` comment stating
why it is sound: which handles are valid and owned, which lock provides the
external synchronization Vulkan requires, and how long the memory a call reads
lives. An `unsafe fn` documents its contract in a `# Safety` section.

## Types

Validate data where it enters the engine, in the constructor of the type
that holds it, such as `AssetHandle` or `Version::from_str`; code that takes
the type never checks it again. Match engine enums exhaustively. Behaviour
belongs on the type that owns it, as a method; free functions are for small
helpers with no owner. Use macros (`dirk_proc`, or `macro_rules!` like the
renderer's descriptor sets) for repeated boilerplate.

## Tests and docs

Tests prove one behaviour each, named for it, and assert the outcome. The
renderer's GPU code has no tests that need a device; test the logic around it,
such as the frame graph's barriers, without one. `dirk_rhi`'s integration
tests are the exception: they run on a device when the machine has one and
skip otherwise, unless `DIRK_REQUIRE_GPU=1` (see its README).

Write a test at the lowest layer that fails without the change, once, not
again in each caller. When a test or table already covers the behaviour, add
a row or an assertion to it rather than a new test. A fix to logic, data or
state comes with a test written first, which fails without the fix; a purely
visual fix, such as spacing or colour, is shown with before and after
screenshots in the pull request instead. An `#[ignore]` says why. Don't write
smoke tests that only check something loads, or tests that a removed feature
stays removed.

Tests wait for events, not time. Never sleep to let something happen, assert
on elapsed time, or poll until something is ready: await the channel,
notification or state change that marks it, such as `Consumer::consume` or an
`AssetLoad`. To move Tokio time, enable Tokio's `test-util` feature for the
crate's tests and use `#[tokio::test(start_paused = true)]`.
A timeout on that wait only guards against a hang. A wait with nothing to
await, such as on a subprocess or on Tokio's runtime shutdown, says why on the
line above: `// wall-clock: <why>`.

Every item has a doc comment saying what it is for and anything not obvious
from its signature. Each crate's README is its crate documentation
(`#![doc = include_str!("../README.md")]`), and rustdoc warnings fail CI.

## Deviations

- Asset loaders return `anyhow::Error`, which `dirk_assets` wraps in
  `Error::AssetLoadError`, so a loader's own errors aren't typed yet.
- `dirk_engine`, `dirk_shaders`, the shaders (`dirk_shaders_gpu`),
  `dirk_threads` and `dirk_editor` have no README yet.
